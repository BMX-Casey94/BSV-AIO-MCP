## Problem addressed
The specification says traditional software integrity controls digitally sign executables with a key pair whose public key comes from a central certification authority, and that a licence governing use or redistribution can be unlawfully transferred with the software. It seeks a way to secure a controlled digital resource (computer software), control access to it, and record that control on a peer-to-peer ledger without changing the underlying blockchain protocol.

## Core mechanism
A node hashes the software executable to H1, hashes licence-related data D1 together with the executable (or H1) to H2 — H2 may be a Merkle-tree top hash over licence leaves such as D1, the executable, user public keys and an expiry date — and stores D1 and H1 in a DHT keyed by H2, optionally with a location identifier (URL or repository pointer). Metadata M containing H2 is placed in a Bitcoin-style P2SH redeem script with an agent public key; a first output locks cryptocurrency C1 to that script on the ledger. Access for a user is authorised by a second redeem script that adds the user’s public key and a second output that spends C1. Location lookup reads H2 from the on-chain redeem script and queries the DHT.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method that determines data D1 associated with the software, a first hash H1 of the executable, and a second hash H2 based on D1 and the executable; stores D1, H1 and H2 in a DHT with H2 as the key of the key-value pair; and determines metadata M comprising H2 for storage on a peer-to-peer distributed ledger.

## BSV relevance
The embodiment is written against the Bitcoin blockchain, P2SH redeem scripts, metadata in public-key slots, DHT look-ups keyed by a hash, and Merkle-hashed licences. Those are the same primitives used on BSV for tokenised access control and off-chain pointers.
