## Problem addressed
The specification says Bitcoin-style OP_CHECKMULTISIG redeem scripts grow linearly with both the number of required signatures M and the number of public keys N, so large multisignature spends need more bandwidth, storage and opcode work. Modular inversion (extended Euclidean algorithm) cannot be done in Script, so elliptic-curve point addition cannot be computed inside the script either.

## Core mechanism
Point addition P3 = P1 + P2 is computed off-chain. The spending transaction supplies P1, P2, the candidate sum P3, and the gradient λ of the line through P1 and P2. An on-chain function PointAdd checks, using only Script arithmetic (subtract, multiply, MOD, EQUAL), that λ is that gradient (distinct-point or doubling case) and that P3’s coordinates satisfy the secp256k1 addition formulae. PointAddMulti chains those checks to verify P = P1 + … + Pn. A first transaction locks a resource to a public-key combination verification function; a second transaction redeems it by presenting the keys, gradient(s) and group public key. Variants add a group ECDSA signature, a Merkle root and a Merkle-path check so the full key list need not sit in the locking script.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method that obtains a first blockchain transaction whose output includes a public-key combination verification function; determines the gradient between a first and a second elliptic-curve public key; and provides a second transaction whose input contains those keys, the gradient and a group public key equal to their point sum, the first transaction being redeemable when the function verifies that sum.

## BSV relevance
The embodiment is written as Bitcoin Script opcodes on secp256k1 public keys. Verifying key aggregation in Script is directly applicable to compact multisignature and group-key spends on BSV.
