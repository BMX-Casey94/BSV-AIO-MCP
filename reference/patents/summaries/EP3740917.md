## Problem addressed
The specification says many decisions depend on several factors and on several parties, each assigned one factor, and that the individual choices should all appear in the final outcome. It reviews majority e-voting and mixing authorities, and says it wants the winner to be the unique combination of the parties’ selections (a path through a decision tree), recorded and validated on a blockchain, rather than a simple majority.

## Core mechanism
Each participant supplies a set of first public keys, one per option on their factor; each key is xG for a secret option x, using the homomorphic property of elliptic-curve scalar multiplication. Those keys are combined (sums of public keys) into second public keys, each representing one possible outcome of the tree; corresponding third public keys are circulated so anyone can check the mapping. Participants reveal the private key for the option they actually chose. A voting transaction TC_Voting has an input script that needs those choice signatures and an output script that represents the resulting decision; a payment transaction TP_Payment can be spent only with a signature on the third public key that matches that decision. Commitment, refund (timelocked) and optional supervisor keys are described. The combination of choices, not a majority count, selects the outcome.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method of making a blockchain decision from each participant’s selection: receive per-participant first public keys (each a possible selection, homomorphically related to a first private key); combine them into second public keys for possible decisions; communicate corresponding third public keys; generate a first transaction whose input is satisfied by the chosen first private-key signatures and whose output represents the decision; and generate a second transaction transferring an asset that requires a signature on the third public key matching that decision.

## BSV relevance
The embodiment uses Bitcoin Script multisignature fields as data storage, elliptic-curve public-key homomorphism, and chained commitment/voting/payment/refund transactions. That is a UTXO-script pattern for multi-party decision flows on BSV.
