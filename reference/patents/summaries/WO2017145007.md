## Problem addressed
Ownership of a blockchain-based asset may be split among many holders, and the asset may generate income or impose costs. The specification says there is a need to detect trigger events and then automatically generate and sign blockchain transactions that apportion those amounts according to current ownership, with a public record that reduces reliance on proprietary systems in a dispute.

## Core mechanism
An asset is associated with private keys (optionally derived as sub-keys from a controller via a shared generator value and a common secret) and with an off-chain computing agent. A registry maps owners’ public keys to redeem-script hashes visible in UTXOs, so the current split can be read from the registry plus the UTXO set. A smart contract — stored in a DHT with its hash in transaction metadata — defines payment rules. A master agent authorises subordinate income, cost, netting and notification agents; on a trigger they calculate pro-rata amounts and build Bitcoin transactions (including SIGHASH_ANYONECANPAY stubs that holders complete to pay costs). The racehorse example issues share tokens, bills stable fees, and pays winnings in BTC.

## Independent claims (gist — not legal scope)
The independent system and method define a multi-owner asset with per-owner private keys, a registry of corresponding public keys tied to UTXO redeem-script hashes, a smart contract whose rules automate generation of transfer transactions, and a hierarchy of computing agents (a master managing subordinates) that evaluate those rules and generate a blockchain transaction when a specified event or trigger is detected.

## BSV relevance
The embodiment is built on Bitcoin-style UTXOs, P2SH redeem scripts, metadata tokens, DHT-stored contracts, and off-chain agents (oracles). Those pieces are the same primitives used for tokenised assets and automated payouts on BSV.
