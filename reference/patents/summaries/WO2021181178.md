## Problem addressed
The specification describes granting IoT peers access with blockchain-published digital certificates issued from a dedicated (skIssue, PKIssue) pair. It then states the problem: a permissioned node that becomes faulty or malicious may ignore instructions, file false reports, or command other devices to do harm, and a centralised revoke path is itself a single point of failure.

## Core mechanism
Each bridging node and device has a certificate stored in its own certificate transaction on the blockchain. When a bridging node fails a configured number of times to connect to a peer, it adds its signature to an alert transaction whose output carries an alert message naming the peers and the failed-attempt counts, and sends that transaction to another bridging node, the registration authority, and/or the blockchain network. The registration authority, on obtaining the alert, revokes access for any identified peer whose failed-attempt count meets a threshold by spending the output of that peer’s certificate transaction, which invalidates the certificate. Without a valid certificate the node cannot join or instruct others.

## Independent claims (gist — not legal scope)
Independent claim 1 is a registration-authority method: obtain an alert transaction that identifies bridging nodes or devices and their failed-connection counts, and revoke those whose count meets a threshold by spending the output of each corresponding certificate transaction. Independent claim 8 is a bridging-node method: after a predetermined number of failed connection attempts, sign an alert transaction that records those failures and transmit it to another bridging node, the registration authority, and/or the blockchain.

## BSV relevance
The embodiment treats a blockchain transaction output as the live certificate: spending it is revocation. That on-chain certificate-and-alert pattern applies to BSV-hosted IoT access control.
