## Problem addressed
As a chain grows, every validating node must store and check every transaction, which limits who can participate. Horizontal sharding lets a node join only some shards, but a shard member still needs to validate new blocks without holding transactions that belong to other shards.

## Core mechanism
Each node joins one or more shards. Transactions are allocated by transaction identifier (modulo the number of active shards) or by following a parent–child input link so related spends stay together. A shard member stores UTXO set, mempool, transaction data and block data only for its shards. For each new block it keeps (i) a list of transaction identifiers that belong to its shards and (ii) a Partial Merkle Tree that retains hashes of out-of-shard transactions and placeholders for in-shard ones. The node can recompute the Merkle root from that tree plus its identifier list without the missing transaction bodies, and it validates only in-shard transactions. A modified `addr` message advertises which shards a peer belongs to.

## Independent claims (gist — not legal scope)
A method has a node that belongs to a subset of horizontal shards generate and store new-block data comprising an in-shard transaction-identifier list and a Partial Merkle Tree that includes hashes of out-of-shard transactions and omits hashes of in-shard ones. System and medium claims cover performing that method.

## BSV relevance
The specification names Bitcoin SV as an example cryptocurrency and describes horizontal shards so a node (including a hobbyist with limited storage) can keep only its shard’s UTXO, mempool and Partial Merkle Tree while still checking the block Merkle root.
