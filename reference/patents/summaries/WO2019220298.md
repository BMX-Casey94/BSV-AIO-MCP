## Problem addressed
Oblivious transfer lets a recipient open only one (or a limited number) of files from a set while the sender cannot tell which was chosen. A plain Diffie–Hellman exchange reveals which key is used. The specification wants an elliptic-curve oblivious-transfer mechanism that can run in a blockchain setting, including with keys derived from a master key.

## Core mechanism
Sender and recipient agree a shared third secret C, for example a hash of block height concatenated with a master-key shared secret. The recipient picks the index of the desired sender key and sends a real public key (for which it holds the private key) plus a decoy public key derived from the real key and C, so the sender cannot tell which is genuine. The sender encrypts each secret to the corresponding public key (in the detailed protocol, via XOR with a Diffie–Hellman-style pad W_i = a_i U_i) and returns the ciphertexts. The recipient can decrypt only the secret matching the key for which it knows the discrete log. The sender can check consistency (the two public keys sum to an agreed point). The 1-of-2 step can be repeated to select among n values. Keys may be deterministic sub-keys of an ECDSA master key.

## Independent claims (gist — not legal scope)
The sender-side independent method receives a first public key (recipient can decrypt) and a second public key (recipient cannot), encrypts the corresponding secrets, and cannot distinguish them; it is characterised by generating a third shared secret on which the second public key is based. The recipient-side independent method is the counterpart: send those two keys, receive both encryptions, and decrypt only the selected secret, again with the decoy key derived from the real key and the third secret.

## BSV relevance
The protocol uses Bitcoin block height as a public randomness source and ECDSA/master-key derivation as described for Bitcoin. It can gate which on-chain or off-chain record a counterparty learns without the sender learning the choice.
