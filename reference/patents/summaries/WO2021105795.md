## Problem addressed
The specification wants game elements (cards are the worked example) to be selected so that a game played with a blockchain is provably fair: players can check that dealing and shuffling were not biased, using randomness that includes seeds they themselves supplied.

## Core mechanism
An oracle collects user seed data items, a sequence of public keys (from users and/or the oracle), and a list of game elements of the same length as the key sequence. It builds a game transaction whose output script, using those seeds, generates at least one pseudorandom number (hash of the combined seeds mapped into the element count) and reorders the public keys into a new list — a partial or complete on-chain shuffle. Game elements are bound to keys. A Merkle tree of hashed elements paired with proof tokens (position witnesses) is committed in a commitment transaction; after the fact, players can be given tokens, element identities, and corresponding private keys so they can check the deal. The detailed use case walks through a poker hand: blinds, hole cards, betting, flop, turn, river, showdown, and redemption of winnings, including hands that end without a showdown.

## Independent claims (gist — not legal scope)
Independent claim 1 is an oracle method that takes user seeds, a public-key sequence, and a game-element list, and creates a game-transaction output whose script derives a pseudorandom number from the seeds and emits a reordered public-key list. Independent claim 13 is that blockchain transaction. Independent claims 14 and 15 are computer equipment and a program that perform the method.

## BSV relevance
The embodiment uses blockchain transaction scripts to shuffle key-represented game elements from player seeds. That is relevant to BSV on-chain or script-assisted games that need publicly checkable randomness.
