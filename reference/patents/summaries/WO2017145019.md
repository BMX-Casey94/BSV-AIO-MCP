## Problem addressed
Contract management is described as ad-hoc, with local copies that are hard to agree on in a dispute. There is no generally accepted public registry that lets anyone check whether a smart contract is still open or has been terminated, nor a machine-readable way to publish existence while restricting content and to time-bind, condition-bind, or roll contracts.

## Core mechanism
The formal contract is stored off-chain (for example in a DHT). A blockchain transaction carries metadata with a location identifier and a hash of the contract, and an unspent output represents the contract as open; spending that UTXO terminates it. Publication can use a P2SH redeem script covering the issuer key plus metadata. An off-chain agent watches the UTXO list. Expiry can be enacted with nLockTime / CheckLockTimeVerify. Rollover generates a new key from the previous key, builds a script with the new key, location and hash, and pays currency to that script. Sub-contracts use a seed-derived public key and a deterministic address, stored with a reference to the parent.

## Independent claims (gist — not legal scope)
Both independent methods store a contract in a repository and broadcast a blockchain transaction with a UTXO plus metadata pointing to that location, treating the contract as open until the UTXO is spent. One then renews or rolls the contract by deriving a new key from the previous key and paying into a script that holds the new key, location and hash. The other generates a sub-contract at a deterministic address via a seed-derived public key, a repository reference, and/or a metadata pointer on the parent.

## BSV relevance
The design uses Bitcoin UTXOs as a public validity flag, P2SH metadata tokens, CLTV-style expiry, DHT storage, and deterministic keys — the same toolkit BSV applications use for on-chain contract status and tokenised access.
