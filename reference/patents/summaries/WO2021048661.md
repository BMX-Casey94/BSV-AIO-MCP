## Problem addressed
The specification says more data and even executable files are being stored on-chain, and it wants miners to offer decentralised computation so users need less local processing power. Native Script is stack-based and not Turing complete, so it cannot run that richer logic by itself.

## Core mechanism
A first transaction already on the chain has a Script locking script and, in the same or another output (OP_RETURN, OP_PUSHDATA, or OP_DROP), a portion of Turing-complete, non-stack code. Node software includes an extractor and a program launcher (described as a virtual machine with external libraries). When a second transaction tries to spend the output, the node extracts and runs the second-language code; that code writes at least one value onto the Script stack. The unlocking script reads that value and compares it with a second value taken from the second transaction; validation requires a match (and may require further Script-only conditions). Because validation — and therefore the mining fee — depends on running the embedded code, a miner who wants the fee must execute it. Inputs and outputs of the computation stay on-chain; the heavy evaluation is off-chain.

## Independent claims (gist — not legal scope)
Independent claim 1 is a node method: take a stack-based, non-Turing-complete locking script and a not-yet-recorded spend; extract and run Turing-complete non-stack code from the first transaction; push the result to the stack; run lock and unlock scripts; and validate only if the unlocking script’s comparison of that stack value with a value from the second transaction succeeds. Independent claims 9 and 10 are a program and a node that perform that method.

## BSV relevance
The embodiment is Script plus miner-run second-language code whose result is checked on the stack. That is relevant to BSV nodes or wallets that attach paid off-chain computation to transaction validation while keeping the native locking language as Script.
