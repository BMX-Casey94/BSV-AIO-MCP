# Managing Blockchain Automata
**Date:** 2018-10-21 | **URL:** https://medium.com/@craig_10243/managing-blockchain-automata-f34fe622a6d
**Subtitle:** This umbrella document describes a distributed platform open to public participation for managing the automation of tasks that interfaces…

## Core thesis
An umbrella specification for "Automata-Management": a public-participation botnet of External Autonomous Agents running on remunerated hosts in parallel to the Bitcoin network, executing client functions (contracts, trading, IoT control) with blockchain-based payment, identity and control. The document is explicitly a patent-mapping exercise — each protocol is tagged with a white-paper number (WP0290–WP0312) where "potential patents have been identified" — and it argues bitcoin is the superior platform to Ethereum or Zennet precisely because of its adoption, stability and the DAO's failure.

## Key arguments and claims
- The technical problem: protocols for "a Blockchain-enabled system of Autonomous Agents"; the blockchain's attractions are lower transaction fees, "independence from central authority", privacy, security and robustness.
- A bot is defined by three properties: External (code is not embedded in bitcoin Script — that technique belongs to "an alternative suite of white papers"), Autonomous ("the host machine on which the bot runs does not control the bot but only provides computer resources"), and Agent (it executes logic for a client, not its host).
- Prior art is acknowledged: BOINC projects (SETI@home, Rosetta@home), Gridcoin, Ethereum, Zennet (which "never got off the ground and was replaced by Tau-chain"), and malicious botnets used "since 2001 for denial-of-service attacks, spyware, email spam, click fraud and mining bitcoins" — theirs "shall not be used for malicious purposes".
- Competitive claim: "Bitcoin is by far the largest cryptocurrency with the widest adoption... Bitcoin has a trusted development community yet remains under no central control... The DAO was built on Etheruem but was hacked."
- Three roles: Client (pays for functions), Service Provider (creates and distributes bots, maintains KYC databases, vets clients/hosts on "reputation; credit rating"), and Host (commits CPU and storage).
- Payment facilities (WP0290): fee structures metered by CPU usage, storage, number of executions, execution time, "success criterion", or event triggers; mechanisms include normal bitcoin transactions, "tokenised bitcoin transactions", and payment channels.
- Bot identity and key management (WP0296): each bot's unique identifier is a BCH address derived from an ECDSA master key pair it generates; secret sharing and key splitting can shard private-key knowledge across SP, host, client, "regulatory authority; escrow service; trustee".
- Function secrecy (WP0302): protocols let hosts execute bots whose code is never revealed to them, with bot categorisation/certification (WP0301) as the safety guarantee against liability or harm.
- Codification doctrine: every bot function is reduced to tables and parameterised functions so it can be manually coded, generated by a "Bot Compiler", or run by an interpreter on a trusted server; the communications module (WP0297) includes a code for "send message as bitcoin transaction" with parameters INPUT-TX-ID and BCH-AMT.
- Configuration taxonomy (WP0312): parallel networks (SETI-style), competing networks (brute-force tasks where the winner claims "the 'prize' by unlocking a bitcoin transaction with the solution"), cooperative swarms (fire-spotting drones), bot hierarchies with manager bots (a DASO), and standalone agents (an arbitrage bot on a laptop).
- Worked scenario: client Alice automates a weather-correlation equity strategy — P/E ratios of 17 NYSE stocks, the NYSE index, and an EF5 tornado warning within a 57-mile radius of Stevens Point, Wisconsin, checked hourly "at seven minutes past the hour (she is superstitious)" — with a manager bot triggering a buy via a P2P Exchange Model invitation transaction (WP0153) that carries a bonus-payment output to the SP; Alice pays through a 12-month payment channel with a locktime "payback" transaction.

## How Craig reasons (his model/logic)
Patent-umbrella methodology: survey the prior art, state the "technical problem", then decompose the system into named protocols, flagging each with a white-paper number where patent potential exists and relegating the rest to "an engineering problem". The reasoning is specification-by-enumeration — roles, fee schedules, configuration taxonomies — anchored by one concrete narrative scenario. This is the nChain IP strategy published in the open: the blog post is simultaneously disclosure, claim-staking and marketing.

## Where this contradicts BTC-mainstream logic
- Against Ethereum's world-computer thesis: smart-contract functionality belongs in external agents using bitcoin for payment, identity and control, not in on-chain code; the DAO hack is wielded as proof of the rival model's fragility.
- Against permissionless-anonymity orthodoxy: the platform runs on KYC databases, registration, vetting, formal contracts (stored on a DHT) and even regulatory key-escrow — a compliance-first market, not a trustless free-for-all.
- Inverts the botnet stigma: botnets are recast as legitimate, remunerated distributed infrastructure with controls.
- Era marker: bot identity uses BCH addresses and the text praises bitcoin's "trusted development community" — written in the pre-BSV window (a month before the Nov 2018 split), before his rhetoric turned on the BCH camp as well.
- Mainstream minimalism ("don't build on the base layer") is rejected: the blockchain is used for payments, messaging, record-keeping, contract storage and bot control simultaneously.
