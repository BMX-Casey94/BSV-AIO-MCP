## Problem addressed
The specification says a party that accepts zero-confirmation payments must know whether the inputs are already spent, including spends that sit only in some nodes’ unpublished transaction sets. Mempools are not synchronised, recent blocks can still be reorganised, and asking a node to search the mempool and the last several blocks on every request is expensive.

## Core mechanism
A transmitting entity (typically a blockchain node) builds a Bloom or Cuckoo filter that encodes identifiers of spent outputs — those spent by transactions in its ordered unpublished set and, optionally, those in the last x blocks. Each identifier is based on the creating transaction’s identifier and output index (the text concatenates them as a 40-byte UTXO ID). The filter is given to a receiving entity (a merchant or light client). Because the filter has no false negatives, a “not present” result means the output is not in the encoded spent set and the payment can be accepted at once; a “present” result is only probable, so the receiver may wait, ask for another output, or ask the node to confirm. The node inserts new spends as transactions arrive, archives the filter when a block is published, and may keep only the last few filters. Use cases named include point-of-sale instant payments, extra checks at nodes, and a simple merchant wallet.

## Independent claims (gist — not legal scope)
Independent claim 1 is a transmitting-entity method that generates a first probabilistic filter encoding identifiers of spent outputs and makes it available to a receiver. Independent claim 13 is a receiving-entity method that obtains that filter, obtains output indications, and treats an output as a double-spend attempt according to whether its identifier is in the filter. Independent claims 14 and 15 are computer equipment and a program for those methods.

## BSV relevance
The description targets 0-conf acceptance and unsynchronised mempools on a UTXO chain. Compact spent-output filters from BSV nodes to merchant or light clients would serve the same instant-payment check the specification describes.
