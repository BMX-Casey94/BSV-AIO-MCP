## Problem addressed
A program or smart contract published to a blockchain may need off-chain inputs (real-world state and events) whose truth cannot be checked from ledger data alone. The specification wants those inputs authenticated, with a conversation proof that a Bitcoin-style script can verify and that remains available if recourse is needed.

## Core mechanism
A cryptographically protected session is opened with a computing entity (data source). Input data that will drive the on-chain program arrives over that session, together with a first attestation that the session’s communications occurred — typically a value based on a Merkle-tree root over salted leaves of the conversation, optionally hashed with a time interval. The program is executed on that input to produce a proof of correct execution (the text discusses zk-SNARK-style proofs and a locking script that holds a verification key). A second attestation (a Merkle path to the conversation tree) shows the data came from the source. A later blockchain transaction can lock an asset to an unlocking script that supplies the source public key, a signature over an expected Merkle-root value, and the Merkle path; unlocking spends that asset and a second output records that the proof was valid.

## Independent claims (gist — not legal scope)
A method opens a protected session, receives program input and a first session attestation, executes the program to produce a correctness proof, generates a second attestation of the data source, publishes the proof, then unlocks a first output using a public key, a signature over an expected value and Merkle-path authentication information tied to a Merkle-tree root. System and medium claims cover performing that method.

## BSV relevance
Authenticated off-chain data plus a script-checkable Merkle conversation proof is an oracle pattern for BSV contracts that consume external events while leaving an on-chain recourse trail.
