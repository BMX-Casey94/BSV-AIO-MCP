## Problem addressed
Intrusion detection and prevention systems typically handle each attack independently. Attack details are not shared with other parties, so the same strategy can be reused cheaply across many networks until a vulnerable target is found. Physical honeypots are expensive, and configuring virtual honeypots is complex, while attackers try to recognise decoys from their behaviour.

## Core mechanism
A data manager maintains a centralised database of traffic data from a community of subscribed users and classifies traffic as normal or attacker using signatures, anomalies, blacklists, scan behaviour, and optionally supervised learning such as multi-layer perceptrons. From an attacker profile it determines a honeypot or honeynet configuration and stores both. A local server protection system compares incoming requests against shared profile packages; attacker traffic is redirected to a generated virtual honeypot and a transformed false database, while bona fide traffic is forwarded to the production server. Logged traffic is sent back to update the shared store.

## Independent claims (gist — not legal scope)
One independent method has the data manager receive, process and store multi-user traffic, derive an attacker profile and associated honeypot or honeynet configuration, and supply both to a legitimate user on request. A second independent method has a local system receive those shared profiles, monitor traffic to a network address, match it to an attacker, retrieve the associated configuration from the shared store, and configure a honeypot or honeynet accordingly. An independent system claim covers a security system arranged to perform that local-side method.
