## Problem addressed
Highly available distributed databases that favour availability and partition tolerance sacrifice consistency: concurrent writes can conflict, and a node that reconnects after a partition may miss updates (the text discusses hinted handoff and zombie replicas). The specification wants ordered, attested database updates coordinated by a blockchain.

## Core mechanism
The network is layered: a core of blockchain miners and storage nodes, an intermediate layer of database nodes that are not miners, and an outer client layer. A first database node receives an update request and either applies it locally or forwards it. A client or another node — not the first database node — submits a blockchain transaction that indicates the update (content, a hash commitment, and/or order). The first database node inspects the chain or mempool and applies the update only after that transaction is seen. After a disconnect it scans the chain and mempool for missed indications and catches up. An optional ordering service can serialise competing updates.

## Independent claims (gist — not legal scope)
A method at a first database node receives one or more updates, applies or forwards them, inspects the blockchain or mempool for a transaction that indicates those updates, and conditions applying the updates on that check, the indicating transaction having been sent by a client or by a node other than the first database node. Equipment and program claims cover that method.

## BSV relevance
Using BSV miners as a core log for a distributed database gives an ordered, public attestation of writes and a recovery path after partition, without making every database node a miner.
