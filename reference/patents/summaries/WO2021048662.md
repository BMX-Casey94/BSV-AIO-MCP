## Problem addressed
The specification is about storing genetic data in blockchain transactions. Earlier on-chain genomic platforms are cited; the document focuses on retrieving a target genome that has been stored in compressed form relative to a reference genome, using a document of transaction-identifier pointers, rather than holding whole sequences in one place.

## Core mechanism
An electronic document (itself optionally stored in a source transaction) contains pointers — each a transaction identifier, and for target data optionally a hyperlink with anchor content — to destination transactions. First destinations hold genetic data for parts of a reference genome (typically unencrypted). Second destinations hold corresponding parts of a target genome compressed against that reference, optionally encrypted under one or more access keys, with a message-authentication code, a digital watermark encoded as A/C/G/T in unused chromosome ends, and epigenetic information. A consuming party reads the document, fetches the referenced transactions (including after clicking a hyperlink), decrypts target parts if required using keys or key-derivation material from a providing party (on-chain or via a side channel, possibly from a shared secret), decompresses the target using the reference, and may apply epigenetic data. Questionnaire fields in the document support search.

## Independent claims (gist — not legal scope)
Claim 1 is a consuming-party method: access an electronic document of pointers to blockchain destination transactions, some storing reference-genome data and others storing corresponding target-genome data compressed relative to the reference; fetch genetic data from at least one first and one matching second destination using those identifiers; and decompress the target data using the reference data. Claim 15 is a computer program that performs the method on the consuming party’s equipment.

## BSV relevance
The embodiment stores large scientific payloads in transaction outputs (the background notes rising per-transaction data capacity) and addresses them by transaction identifiers. That matches BSV’s use as a data carrier for documents and scientific datasets, including OP_RETURN-style payloads.
