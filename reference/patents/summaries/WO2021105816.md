## Problem addressed
The specification says certification-authority revocation lists are published slowly, so a certificate may already be revoked when a relying party accepts it, and offline or lightweight (SPV) nodes cannot easily query a UTXO set themselves. A gap also remains between checking a certificate and depending on that check in a later payment. It seeks to record certificates on a blockchain so that validity is the unspent state of an output, and to fold that check into the payment transaction itself.

## Core mechanism
A certificate authority builds a certification transaction: an input signed with the CA key, a first output (P2PKH) to a CA-controlled certification-transaction key, and a second OP_RETURN (or similar) output carrying the subject’s public key. The digital certificate is that public key plus the certification transaction identifier. Revocation is spending the first output; replacement spends it into a new certification transaction. For automated use, the subject (or a counterparty) builds a transaction template whose first input spends that certification output, signed with the certification-transaction key, and which also carries the subject’s public key. The counterparty fetches the certification transaction (or a copy plus Merkle path), checks the CA signature and that the certified key matches, completes the template with its own input or output, and broadcasts it. Network nodes accept the payment only if that certification output is still in the UTXO set — so a revoked certificate fails the spend. Multiple P2PKH outputs on one certification transaction allow a bounded number of uses before revocation.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method at a second node: receive a transaction template whose first input references a certification-transaction output and is signed with a certification-transaction key, and which includes the first node’s public key; obtain the certification transaction and confirm it certifies that key and is signed by a CA key; complete the template; and propagate it so that validation succeeds only if the certification output remains in the UTXO set. Independent claims 14 and 15 cover a computing device and a computer-readable medium that perform the method.

## BSV relevance
The construction uses Bitcoin-style P2PKH, OP_RETURN and the UTXO set as a live revocation oracle, including SPV Merkle-path checks. That is a direct BSV pattern for on-chain PKI and payment-time certificate checks.
