## Problem addressed
Per-peer INV/GETDATA relay of each transaction is a throughput bottleneck (the text cites about 3 transactions per second versus roughly 50,000 for card payments). Applying network coding at every node is described as computationally costly when the node is not actually constraining the flow.

## Core mechanism
A node decides it is a bottleneck when its in-links (fan-in) exceed its out-links (fan-out), either at the moment a first transaction arrives or as averages over time. While that condition holds it accumulates new transactions until a stop condition (a time window or a maximum count). It then linearly combines those transactions with a local encoding vector into one message no longer than the longest transaction, and sends that message plus a recursively derived global encoding vector on its out-links instead of the individual transactions. Receivers recover the originals when the matrix of global encoding vectors has full rank. If the node is not a bottleneck it forwards transactions in the ordinary way.

## Independent claims (gist — not legal scope)
A method dynamically treats a node as a bottleneck when in-links exceed out-links, then network-codes accumulated transactions with a local encoding vector and sends the coded message plus a global encoding vector instead of the individual transactions. A medium claim stores instructions to perform that method.

## BSV relevance
Selective network coding at fan-in/fan-out bottlenecks is a relay optimisation for large BSV transaction and block propagation, where INV/GETDATA chatter remains a practical constraint.
