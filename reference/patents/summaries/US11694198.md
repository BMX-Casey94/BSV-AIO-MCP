## Problem addressed
The specification says earlier Group Random Exchange protocols either share one secret across all channels (which lets an observer cluster the set) or require every participant to send their secret to an initiator before transfers start, which is undesirable when the protocol is used as a building block. It seeks a group exchange that still hides the link between a node’s input and output addresses, without a mixing service and without any node revealing its own secret except inside the transaction that pays that node.

## Core mechanism
Group Random Exchange Late Reveal randomises participating nodes into a cycle and elects an initiator who holds a private ks (with public Ps). Every other node Ui sends only its public Pi = ki G to the initiator. Payment channels are built clockwise. Each channel’s locking value Q_{i+1} is the elliptic-curve sum of public keys from the next node through to the initiator; Ui obtains Qi from its predecessor and subtracts its own Pi to form Q_{i+1}. The payment transaction unlocks on the corresponding private-key sum sv_{i+1}. Channels in a node’s favour are created before the channel in which that node pays. Execution starts at the initiator, who can unlock the last channel with ks alone; each subsequent payer adds its own ki to the revealed sum (anticlockwise) and only then discloses a result that includes its secret, inside the transaction that pays it. Locktimed refunds reclaim funds if the sequence stalls.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method performed by a non-initiator node Ui: it generates a key pair, sends its public key to the initiator, receives from the previous node a first value based on public keys from itself through to the initiator, derives a locking value, and opens a payment channel (commitment, refund, payment) whose payment unlocks with a value based on the private keys from the next node through to the initiator. Independent claims 14 and 15 cover a computing device and a storage medium that perform that method.

## BSV relevance
The protocol is specified with Bitcoin payment channels, script locks that take an elliptic-curve secret, and nLockTime refunds. It is relevant to BSV only where a user-controlled cyclic exchange is implemented to unlink addresses.
