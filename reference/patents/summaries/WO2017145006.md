## Problem addressed
Bitcoin-style scripts are limited to linear or tree-like decision tasks and do not natively support loops, which restricts automated process and device control. Platforms that add an on-chain Turing-complete language introduce infinite-loop and denial-of-service risks. The specification wants looping and other Turing-complete control flow combined with a restricted blockchain script, without putting those loops inside the script itself.

## Core mechanism
An off-chain computing resource (called the Manager, oracle or bot) runs in parallel with the blockchain and treats the ledger as a Turing machine’s non-erasable tape. The Manager executes a repeat loop whose body is an “if condition then action” (ICTA) block: it watches the chain (and optional off-chain inputs) for start, repeat or stop conditions, then either broadcasts a new transaction or performs an off-chain action. Iteration state and a hash of the loop code are stored as metadata in multi-signature P2SH transactions; the Manager can respawn the loop at a given iteration by looking up that hash in a code registry. Software updates can be authorised mid-loop with a multi-signature P2SH that records hashes of the old and new code. An example embodiment is an automated vote-counting bot that stores intermediate counts on chain.

## Independent claims (gist — not legal scope)
A method and a matching system execute a loop on a computing resource, store iteration information as metadata in a blockchain transaction, and steer the loop by watching the chain for transactions that match a start or triggering condition, a repeat condition or a stop condition.

## BSV relevance
The described Manager-plus-metadata pattern is a way to add looping process control around Bitcoin-style Script without putting loops in Script itself — relevant to BSV oracles, IoT control and on-chain audit of automated workflows.
