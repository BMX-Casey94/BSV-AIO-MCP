## Problem addressed
An overlay such as Metanet stores content in blockchain transaction payloads and links those transactions in a graph that need not match spend edges. Each overlay node may need several keys (write/structure, encryption, funding). The specification says it would be more effective if a key set’s derivation graph matched the overlay graph, so a node’s key is fixed by seed plus graph position, and so write keys can be shared without revealing encryption or funding keys.

## Core mechanism
A first software module reads the overlay graph (nodes = data-storage transactions, edges = overlay links). First keys, derived from a first seed, sign the parent input that authorises writing a child overlay transaction. A child-key-derivation (CKD) function is applied to a second seed to build a second hierarchical key set with the same graph; those keys are not used to sign data-storage inputs but for an extra function (obfuscation/de-obfuscation, funding, or an application-layer function). The first module can send only a graph position to a second module, which derives the first key from the first seed and CKD. The second seed is withheld, so a service provider can be commissioned to write Metanet transactions without being able to decrypt content. A third seed can yield a third parallel key set. Seeds may come from one master seed. HD-wallet homomorphism is used so child public keys can be derived from an extended parent public key without storing child private keys.

## Independent claims (gist — not legal scope)
Claim 1 is a method of managing an overlay on data-storage transactions: identify the overlay graph; associate each node with a first key from a first seed for signing a child’s write; and apply CKD to a second seed to obtain second keys on the same graph for an additional function other than signing those inputs. Claim 16 is a second-module method: receive a graph position, derive the corresponding key from a seed and CKD, and use it for a function other than signing the data-storage input.

## BSV relevance
The specification is written around Metanet on a Bitcoin-style UTXO chain, OP_RETURN payloads and HD wallets. That is relevant to BSV overlay data graphs and to splitting write, fund and encryption key domains for on-chain content.
