## Problem addressed
Organisations want blockchain records alongside internal databases, but the ledger does not interoperate with those systems and locating the relevant transactions among blocks is slow and insecure if done naively. The specification wants a way to identify, extract and forward blockchain transaction data to a non-blockchain resource without changing either platform.

## Core mechanism
Public addresses of entities are classified by identifiers of a first type arranged as a tree that links parent and child entities. Deterministic keys are derived from that tree: a parent key from a parent indication, and a child key from the parent key plus a child indication. Given a first identifier, the method selects the matching address subset and searches the chain for transactions that use those addresses. Extracted data can be turned into reports that are hashed and combined (including a hash of concatenated report hashes). A second classification (for example account type) can further narrow the address set. Associations may be stored in a look-up table or written into the ledger with a script.

## Independent claims (gist — not legal scope)
A method and system classify entity public addresses by tree-structured deterministic-key identifiers, receive an identifier for one entity, resolve that entity’s addresses, and find blockchain transactions that use those addresses, with parent and child deterministic keys generated as described above.

## BSV relevance
Hierarchical deterministic address classification and on-chain look-up of an organisation’s transactions is usable for BSV accounting, reporting and wallet-tree tooling that already derives keys from a root.
