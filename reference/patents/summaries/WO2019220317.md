## Problem addressed
The specification says tokens that grant access to a resource (computing session, room, vehicle, goods, website) need to be communicated, stored, generated and transferred securely while using as little computing resource as possible. Direct client–server token exchange can be intercepted, and storing every token is expensive.

## Core mechanism
A client and server share a one-way function chain (typically a hash chain). The server is given only a verification item (a later chain value). The client activates a token by submitting the previous chain item in an access blockchain transaction. The server hashes that item and compares it with the stored verification item; on a match it grants access to the associated resource, replaces the verification item with the just-seen item, and may delete the old one. Only an initial seed need be stored to regenerate the chain. Tokens can be recorded as public keys derived from a base public key plus a chain item. Transfer of remaining access uses an exchange transaction that unlocks when a verification item of the old chain and of a new chain are presented, with a timelocked return transaction if the swap is not completed.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method in which a first party gives a second party a verification item from a one-way function chain, then submits an access transaction containing a chain item; the second party applies the one-way function, compares the output with the verification item, and on success treats that item as the next verification item and grants access to the resource associated with it.

## BSV relevance
The embodiment uses the blockchain as the channel that carries each successive hash-chain token, with optional public-key embedding of the token. That is a standard BSV pattern for sequential access tickets and metered resources.
