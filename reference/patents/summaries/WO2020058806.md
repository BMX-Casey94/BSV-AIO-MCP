## Problem addressed
A prior two-node method can compute a common secret from each side’s private key and the other’s public key. The specification wants the same style of secret to be shared among at least three nodes, efficiently and so that individual pairwise secrets can be obscured when values appear (for example) in blockchain scripts.

## Core mechanism
Each node has an asymmetric key pair on a common (typically elliptic-curve) system. A first node computes pairwise second common secrets with each second node as (own private key)×(their public key), matching what the peer computes the other way. Shares of a group first common secret are built from those pairwise secrets (XOR or modular products, or as points on a polynomial needing a threshold to interpolate). Each share is encrypted under a key derived from the pairwise secret with the intended recipient and sent; the first node also receives the peer’s encrypted share. Optional deterministic child keys V_2C = V_1C + hash(M) and P_2S = P_1S + hash(M)×G bind the exchange to a message. The reconstructed first secret can then key symmetric encryption of messages or transaction payloads.

## Independent claims (gist — not legal scope)
The independent sharing method determines pairwise second common secrets between a first node and second nodes, and third common secrets between those second nodes and further nodes; encrypts shares of a first common secret under keys based on the pairwise secrets; and exchanges the encrypted shares so a threshold of shares (not fewer) can recover the first secret. Further independent claims apply that shared secret as a symmetric key for secure communication or an online transaction among the nodes.

## BSV relevance
The specification names digital wallets and Bitcoin as intended settings and discusses putting combined secrets in transaction scripts. The same pairwise-to-group secret can key encrypted payloads or multi-party wallet coordination on BSV.
