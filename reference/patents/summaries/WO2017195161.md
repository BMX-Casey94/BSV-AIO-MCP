## Problem addressed
Software is commonly signed with keys from a certification authority and shipped with a licence, but it can still be transferred or installed without authorisation. The specification wants ownership of a controlled digital asset (especially computer software) checked at install time, using both a distributed hash table and a blockchain rather than a single trusted authority.

## Core mechanism
A first hash (H1) is taken of the software executable and a second hash (H2) of licence-related data plus the software; H2 is the DHT key and D1 plus H1 are the value, optionally with a location pointer. Metadata based on H2 is placed in a P2SH redeem script on the ledger. To verify ownership, a second-user public key is read from a ledger transaction and another public key for that user is read from the DHT; ownership is accepted if the keys match. The executable may first be encrypted with a common secret derived from generator-value-adjusted key pairs of vendor and user, then decrypted and installed, optionally gated by an activation key. A Merkle tree can bind licence leaves (data, executable hash, public keys, expiry) into H2.

## Independent claims (gist — not legal scope)
A method, program and system verify software ownership for installation by comparing a second-user public key taken from a ledger transaction with a second public key taken from a DHT entry and treating a match as verification of ownership.

## BSV relevance
Splitting licence state between a DHT and a BSV P2SH metadata transaction, then matching keys at install, is a concrete pattern for BSV-anchored software licensing without a central certificate authority.
