## Problem addressed
Tokens (coloured coins) can represent contracts or assets by embedding metadata in a redeem script hashed into a P2SH output. A transfer that is not countersigned by the issuer or another authorised party leaves the recipient without an obvious way to confirm the token is legitimate. The claimed work is directed at validating such unsigned tokens.

## Core mechanism
An issuer tokenises a quantity of cryptocurrency by locking it to a P2SH redeem script that embeds contract metadata (type, pointer, hash) plus user and issuer public keys. Transfers rewrite the redeem script to the new holder. A title-registry store — optionally a DHT, maintained by monitoring the blockchain for token metadata — records transfer transaction identifiers and output scripts. To validate a received token, a party first queries that registry for a prior transfer of the same token; if none is found, it walks previous-transaction IDs on the blockchain until it finds a redeem script signed by an authorised signatory, or exhausts the chain.

## Independent claims (gist — not legal scope)
The independent method has a recipient query a monitored title-registry database for a prior token-transfer transaction (matching transaction indicators and output-script metadata). If that record is missing, the recipient iteratively follows previous-transaction IDs on the blockchain until a redeem script signed by an authorised signatory is found, and treats the token as valid if either check succeeds. Independent claims also cover a validation system and software that perform that method.

## BSV relevance
The embodiment is a Bitcoin P2SH token with metadata in the redeem script, UTXO chaining, and optional DHT registries — the same pattern used for coloured-coin and contract tokens on BSV.
