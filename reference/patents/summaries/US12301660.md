## Problem addressed
The specification says proof-of-work block confirmation (about ten minutes in the Bitcoin example) and a throughput of about three unconfirmed transactions per second cannot support high-volume exchanges such as card-like payments at tens of thousands of transactions per second. It also says storing a full mempool at every node becomes untenable as volume grows. It seeks specialised nodes that validate and push unconfirmed transactions faster without requiring every such node to hold the entire pending set.

## Core mechanism
A subset of nodes (“merchant” or specialised network nodes) form an overlay. They do not mine or store the full chain. Their shared mempool is a distributed hash table: each specialised node stores only an assigned, partly overlapping slice so each pending transaction lives on at least two specialised nodes but not all of them. On receiving a transaction, a specialised node hashes the transaction identifier to a key, checks whether that key is already in the DHT, stores the transaction if not, and forwards the transaction to ordinary (non-specialised) nodes over peer-to-peer connections. Transactions stay in the DHT until a configured number of block confirmations, so orphan blocks do not force a full rebroadcast. Neighbouring specialised nodes are scored in a reputation table and isolated if the score falls below a threshold.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method in which specialised nodes hold a DHT mempool of pending transactions: a node receives a transaction, hashes its identifier to a key, stores it in the DHT if absent, and sends it to non-specialised nodes over peer-to-peer connections. Independent claim 8 is a specialised network node with processor, DHT slice, network interface and application instructions that perform those steps. Independent claim 15 is a non-transitory medium with instructions to carry out the method.

## BSV relevance
The overlay-plus-DHT mempool is specified for Bitcoin-family networks that need faster unconfirmed-transaction fan-out without every specialised node holding a full pending set. That path is relevant to BSV node implementations that propagate pending transactions the same way.
