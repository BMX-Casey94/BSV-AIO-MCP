## Problem addressed
The specification says conventional transfers (bank payments, foreign-exchange) are slow and costly, and that known blockchain exchanges still rely on third-party escrows and multi-currency processors. It seeks a way for parties to offer, request and exchange entities — cryptocurrency, contracts, goods or services — on a peer-to-peer ledger, with a permanent record of invitation and exchange, without altering the underlying blockchain protocol.

## Core mechanism
A user invitation is encoded as metadata (entity, conditions such as price ranges, exchange rate, deadline, geography) in a redeem script together with the user’s public key and a third-party (escrow) public key; the script is hashed and locked in a P2SH invitation transaction. The full script and hash may be published on a DHT so the hash is a look-up key; metadata occupies script slots designated for public keys. Matching invitations are paired when conditions overlap. Exchange is completed by broadcasting one or two exchange transactions that spend the invitation outputs, presenting scripts signed by the users and third parties, and paying tokenised entities to the counterparties. Tokens are issuer-signed contracts, divisible or not, optionally pegged to the underlying bitcoin amount.

## Independent claims (gist — not legal scope)
Independent claim 1 is a method that generates and broadcasts a first exchange transaction spending a prior invitation output, with a script that contains issuer-signed token metadata for the entity and transfer conditions, the first user’s public key, and a first third-party public key, signed with the matching private keys, and an output transferring the tokenised entity to a second user.

## BSV relevance
The embodiment is built on Bitcoin P2SH, Script public-key slots used as metadata carriers, DHT-backed invitation records, and issuer-signed tokens. That maps onto BSV script, token and off-chain pointer patterns for peer-to-peer exchange.
